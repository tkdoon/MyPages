OAuth 2.0 をやさしく理解する

「Googleでログイン」の裏で何が起きているのか。パスワードを渡さずに権限を委譲する仕組みを一から解説します。

OAuthとは 認証フロー6ステップ なぜコード交換が必要か サーバーの内部構造 CSRFとstate セッションの仕組み

Section 01

OAuthとは何か

「パスワードを渡さずに、他サービスへのアクセス権限を委ねる」仕組みです。

🏨 ホテルのたとえ ホテルに「会員証（Google）でチェックインしたい」と伝えると、フロントは会員証の窓口に誘導します。あなたは会員証の暗証番号をホテルに教えることなく、ホテルはあなたの会員情報を確認できます。これがOAuthの本質です。

OAuthなしの世界

  • アプリにパスワードを直接渡す
  • アプリが漏洩したらパスワードも漏れる
  • 権限の範囲を絞れない
  • 連携を取り消す手段がない

OAuthありの世界

  • パスワードはGoogleだけが知る
  • アクセストークンに有効期限がある
  • 権限（scope）を細かく指定できる
  • いつでも連携を取り消せる

登場人物

📱

アプリ（クライアント）

あなたが使うサービス

Googleログインを「使う側」。ユーザーのGoogleデータにアクセスしたい。

🔐

認証サーバー（Google等）

ログインとトークン発行を担う

本人確認を行い、許可された範囲でトークンを発行する「信頼の起点」。

Section 02

認証フロー 6ステップ

「Googleでログイン」ボタンを押してから完了するまでの全プロセス。

01

「Googleでログイン」ボタンを押す

アプリが「どのサービスで認証するか」「どんな情報が必要か（scope）」を準備する。

02

Googleのログイン画面へリダイレクト

ブラウザが自動でGoogleのページに移動。URLにアプリID・権限・返却先URLが付く。

https://accounts.google.com/o/oauth2/auth?client_id=...&scope=email&redirect_uri=...
03

パスワード入力 ＆ 権限に同意

パスワードはGoogleにだけ送られる。アプリはパスワードを一切知らない。これがOAuthの核心。

04

認証コード（引換券）をアプリに返す

GoogleがコールバックURLに短命の認証コードを付けてリダイレクト。数分で失効し、単体では何もできない。

https://myapp.com/callback?code=X9f2kA...&state=a3f9X...
05

認証コード → アクセストークンに交換

アプリのサーバーがGoogleに「コード＋シークレットキー」を送り、アクセストークンを受け取る。ブラウザを介さないサーバー間通信。

06

アクセストークンでデータ取得

トークンを使ってGoogle APIを叩き、プロフィールやメールなどを取得。トークンには有効期限があり、リフレッシュトークンで再取得可能。

Section 03

なぜ認証コードとトークンを交換するのか

直接アクセストークンをURLで返さない理由は、「URLは危険な場所」だからです。

危険なパターン（直接返す）

  • トークンがURLに露出する
  • ブラウザ履歴に残る
  • Refererヘッダーで外部に漏れる
  • サーバーアクセスログにも残る
  • トークン＝即使える鍵なので致命的

安全なパターン（コード経由）

  • コード単体では何もできない
  • 交換にシークレットキーが必要
  • トークンはURLに一切現れない
  • コードは1回しか使えず即失効
  • 正規アプリのみトークン取得可能

交換リクエストの中身

POST https://oauth2.googleapis.com/token
grant_type = authorization_code
code = X9f2kA... # ブラウザ経由の認証コード
client_id = my-app-id
client_secret = s3cr3t!! # サーバーにしかない秘密鍵
redirect_uri = https://myapp.com/callback
🔑 client_secret がすべての要 Googleはこの5つをすべて照合して初めてトークンを発行します。認証コードを盗んでも、client_secretなしでは交換できません。このシークレットは絶対にブラウザ側（フロントエンドのJSコード）に置いてはいけません。

Section 05

CSRF攻撃とstateによる防御

stateは「このコールバックは、自分が始めたフローのものか？」を確認する合言葉です。

😈 CSRF攻撃のシナリオ 攻撃者が自分のGoogleアカウントで認証コードを取得 → そのコールバックURLを被害者に踏ませる → 被害者のセッションで攻撃者のコードが処理される → 被害者のアカウントに攻撃者のGoogleが連携されてしまう。

stateによる防御フロー

①

ログインボタンを押した瞬間にstateを生成

暗号論的に安全なランダム文字列をサーバーのセッションに保存する。

session["oauth_state"] = "a3f9Xk2mQ7..."
②

stateをGoogleへのリダイレクトURLに含める

https://accounts.google.com/...&state=a3f9Xk2mQ7...
③

Googleがstateをそのままコールバックに付けて返す

Googleはstateの中身を見ない。ただそのまま返すだけ。

?code=...&state=a3f9Xk2mQ7...
④

セッションのstateと照合 → 一致したらフロー続行

攻撃者は別ユーザーのセッションを読めないためstateを偽造できず、必ず不一致になる。

🛡️ stateの3つの性質 予測不可能：推測できる値（123など）は意味がない。暗号論的乱数を毎回生成する。
一度きり：使い終わったstateはセッションから即削除する。再利用を防ぐ。
セッションに紐付き：URLではなくサーバーのセッションに保存。他ユーザーから読めない。

Section 06

サーバーサイドセッションの仕組み

HTTPは「ステートレス（記憶を持たない）」な仕組みです。セッションはこの問題を解決します。

📦 セッション＝「サーバー側の引き出し」 ブラウザには引き出しの「鍵（セッションID）」だけを渡し、実データはすべてサーバー側の引き出しに保管する。鍵だけ持っていても中身はわからないし、改ざんもできない。

ブラウザとサーバーの役割分担

🍪 ブラウザ（クッキー）

session_id"e7a2f9c3b1..."

← 鍵だけ持つ。中身は知らない

⟷

🗄️ サーバー（引き出し）

user_id42
name"田中"
logged_intrue
access_token"ya29.A0..."

← 実データはここだけ

クッキーの重要フラグ

  • HttpOnly JSからクッキーを読めなくする。XSS攻撃でトークンが盗まれなくなる。
  • Secure HTTPS通信のときだけクッキーを送信する。平文通信での漏洩を防ぐ。
  • SameSite 別サイトからのリクエストにクッキーを自動送信しない。CSRF対策の第2の壁。

OAuthフロー中のセッションの変化

session の中身の変化
# フロー開始時
{ oauth_state: "a3f9Xk2mQ7..." }

# state照合後（削除）
{ }

# ログイン完了後
{ user_id: 42, access_token: "ya29.A0ARrda..." }

Summary

全体のまとめ

OAuthのセキュリティは、いくつかの「分離」の原則に支えられています。

01

パスワードの分離

パスワードはGoogleだけが知る。アプリはパスワードに触れない。

02

URLとトークンの分離

トークンはURLに乗らない。サーバー間の秘密チャンネルで交換する。

03

秘密鍵の分離

client_secretはサーバーにだけ存在。ブラウザ側には絶対に置かない。

04

データとIDの分離

セッションの実データはサーバーに。ブラウザにはIDだけを渡す。

05

フローの起点確認

stateでコールバックが自分が始めたフローかを照合。CSRFを防ぐ。

06

時間による制限

認証コードは数分、アクセストークンは数時間で失効。被害を限定する。
