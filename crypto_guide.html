暗号のしくみ

シーザー暗号から RSA、楕円曲線、TLS 1.3、耐量子暗号まで。数式は小さな数で手を動かしながら、何がなぜ安全なのかを順に説明します。

公開してよいもの公開鍵、公開値、暗号文など。盗聴者に見られても安全性は崩れません。
秘密にするもの秘密鍵、共通鍵、選んだ素数など。漏れた時点で安全性が失われます。

第1章暗号が守るもの

「暗号」というと内容を隠すことを思い浮かべがちですが、現代の暗号技術が守っているのは秘密だけではありません。情報セキュリティでは、暗号に期待する役割を大きく4つに分けて考えます。

性質意味主な技術
機密性許可された人以外には内容が読めない共通鍵暗号、公開鍵暗号
完全性途中で書き換えられていないことがわかるハッシュ関数、MAC、AEAD
認証通信相手やデータの作成者が本物だとわかるMAC、デジタル署名、証明書
否認防止作成者が後から「自分ではない」と言えないデジタル署名

もう一つ重要な考え方がケルクホフスの原理です。「暗号の安全性は、方式（アルゴリズム）が知られていても鍵さえ秘密なら保たれるべきだ」というもので、19世紀に提唱されました。現代の標準暗号はすべて仕組みが公開されており、世界中の研究者が攻撃を試みても破られないことで信頼を得ています。方式を隠すことで安全を保とうとする「隠蔽によるセキュリティ」は、仕組みが漏れた瞬間に崩れるため推奨されません。

第2章暗号の歴史

暗号の歴史は、作る側と破る側の競争の歴史でもあります。主な出来事を時系列で並べます。

  1. 紀元前1世紀ユリウス・カエサルが、文字をアルファベット順に3つずらすシーザー暗号を使ったとされる。
  2. 9世紀アラブの学者アル＝キンディーが頻度分析を記述。文字の出現頻度の偏りから単純な置換暗号が解けるようになる。
  3. 16世紀ヴィジュネル暗号が登場。鍵となる単語に従ってずらす量を文字ごとに変え、頻度分析を難しくした。
  4. 1917年バーナムが鍵とメッセージを排他的論理和で組み合わせる方式を考案。後のワンタイムパッドの原型となる。
  5. 1940年代第二次世界大戦で独軍の暗号機エニグマが使われ、英国のチューリングらがその解読に成功する。
  6. 1949年シャノンが情報理論に基づき、使い捨ての真の乱数鍵（ワンタイムパッド）が理論上解読不能であることを証明。
  7. 1976年ディフィーとヘルマンが公開鍵暗号の概念と鍵共有方式を発表。鍵配送問題に解決の道が開かれる。
  8. 1977年リベスト、シャミア、エーデルマンが RSA を発表。同年、DES が米国の標準暗号になる。
  9. 1985年コブリッツとミラーがそれぞれ楕円曲線暗号を提案。
  10. 2001年公開コンペを経て Rijndael が AES として米国標準に採用され、DES の後継となる。
  11. 2018年TLS 1.3 が RFC 8446 として標準化。前方秘匿性のある鍵共有が必須になる。
  12. 2024年NIST が耐量子暗号の最初の標準（FIPS 203・204・205）を発行。

シーザー暗号を試す

シーザー暗号の「鍵」はずらす量だけなので、候補は25通りしかありません。全部試せばすぐに解けてしまいます。この「鍵の候補の数」を鍵空間と呼び、現代の暗号では 2¹²⁸ 以上が標準です。

第3章共通鍵暗号

暗号化と復号に同じ鍵を使う方式です。対称鍵暗号とも呼ばれます。計算が非常に速く、大量のデータの暗号化はほぼすべてこの方式で行われています。

ブロック暗号とストリーム暗号

ブロック暗号はデータを決まった長さ（AES なら128ビット＝16バイト）のブロックに区切り、ブロックごとに変換します。現在の標準は AES で、鍵長は128・192・256ビットから選べます。内部では、バイトの置き換え、行のずらし、列の混ぜ合わせ、鍵との排他的論理和を1ラウンドとして、10〜14ラウンド繰り返します。多くの CPU に AES 専用の命令が組み込まれており、ハードウェアで高速に処理できます。

ストリーム暗号は、鍵から疑似乱数の列（鍵ストリーム）を作り、データと1ビットずつ排他的論理和を取ります。代表は ChaCha20 で、AES 命令を持たないスマートフォンなどでも高速に動くため、TLS で AES と並んで広く使われています。

暗号利用モード

ブロック暗号で長いデータを暗号化するときの「ブロックのつなぎ方」を暗号利用モードと言います。選び方を誤ると、AES 自体が強くても安全性が崩れます。

モード仕組み評価
ECB各ブロックを独立に暗号化同じ平文ブロックが同じ暗号文になり、画像を暗号化すると輪郭が透けて見える。使ってはいけない
CBC前の暗号文ブロックを次の平文に混ぜる古い方式。改ざん検知がなく、実装次第でパディングオラクル攻撃を受ける
CTRカウンターを暗号化して鍵ストリームを作るブロック暗号をストリーム暗号として使う。単体では改ざん検知がない
GCMCTR に改ざん検知用のタグ計算を組み合わせる現在の標準。暗号化と完全性の確認を同時に行う

GCM のように、暗号化と改ざん検知を一体で提供する方式を AEAD（認証付き暗号）と呼びます。TLS 1.3 で使える共通鍵暗号は AES-GCM、ChaCha20-Poly1305 などの AEAD だけです。

ナンスの使い回しに注意。 GCM や ChaCha20 では、暗号化のたびに「ナンス」と呼ばれる一度きりの値を使います。同じ鍵で同じナンスを2回使うと、2つの平文の排他的論理和が漏れ、GCM では改ざん防止の鍵まで推測されてしまいます。

鍵配送問題

共通鍵暗号の最大の弱点は、通信を始める前に相手と同じ鍵を共有しなければならないことです。盗聴されている通信路で鍵をそのまま送れば盗まれ、鍵を暗号化して送ろうとすると「その鍵をどう渡すか」という同じ問題に戻ってしまいます。この堂々巡りを解決したのが、第5章・第6章の公開鍵暗号と鍵共有です。

第4章ハッシュ関数と MAC

暗号学的ハッシュ関数は、任意の長さのデータから固定長の値（ハッシュ値、ダイジェスト）を計算する関数です。データの「指紋」のようなもので、鍵を使わず、誰が計算しても同じ結果になります。暗号化とは違い、ハッシュ値から元のデータに戻すことはできません。

安全なハッシュ関数には次の3つの性質が求められます。

  • 原像計算困難性：ハッシュ値から元のデータを求められない。
  • 第二原像計算困難性：あるデータと同じハッシュ値になる別のデータを見つけられない。
  • 衝突困難性：同じハッシュ値になるデータの組を、どんな組でもよいから見つけられない。

さらに、入力が1ビット変わるだけで出力のおよそ半分のビットが変わる「雪崩効果」があります。現在の標準は SHA-256 などの SHA-2 ファミリーと SHA-3 です。MD5 と SHA-1 は衝突が実際に作られており、署名などの安全性が必要な用途には使えません。

SHA-256 の雪崩効果1文字だけ変えてみてください

MAC：鍵付きのハッシュ

ハッシュ値だけでは改ざんは防げません。攻撃者がデータを書き換えたうえで、ハッシュ値も計算し直せばよいからです。そこで共通鍵を混ぜて計算するのが MAC（メッセージ認証コード）です。鍵を知る人しか正しい値を作れないので、改ざんの検知と送信者の確認ができます。代表的なものは HMAC-SHA256 です。ただし送受信者が同じ鍵を持つため、「どちらが作ったか」を第三者に証明すること（否認防止）はできません。それにはデジタル署名が必要です。

パスワードの保存

サービスがパスワードを保存するときは、平文ではなくハッシュ値を保存します。ただし SHA-256 は高速すぎるため、漏洩したハッシュ値に対して GPU で毎秒何十億回も総当たりされてしまいます。パスワード保存には、わざと計算を重くし、大量のメモリを必要とするよう設計された Argon2id、scrypt、bcrypt を使います。また、ユーザーごとに異なるランダムな値（ソルト）を混ぜることで、同じパスワードでも異なるハッシュ値になり、事前計算した対応表（レインボーテーブル）による攻撃を防ぎます。

第5章公開鍵暗号と RSA

公開鍵暗号では、暗号化に使う公開鍵と復号に使う秘密鍵が別々です。公開鍵は誰に見せてもよく、それで暗号化されたデータは秘密鍵の持ち主しか復号できません。代表的な方式が RSA で、「2つの素数を掛けるのは簡単だが、積から元の素数を求める（素因数分解）のは非常に難しい」という性質に安全性の根拠を置いています。

鍵の作り方

  1. 大きな素数 p と q を選ぶ。
  2. n = p × q を計算する。
  3. φ(n) = (p − 1)(q − 1) を計算する。
  4. φ(n) と互いに素な e を選ぶ（実用では 65537）。
  5. e × d を φ(n) で割った余りが 1 になる d を求める。

公開鍵は (e, n)、秘密鍵は d です。暗号化と復号は次の式で行います。

暗号化　c = me mod n
復号　　m = cd mod n

元に戻る理由はオイラーの定理です。ed は φ(n) の倍数＋1 なので、m を ed 乗すると mod n で m に戻ります。攻撃者が d を求めるには φ(n) が必要で、それには n の素因数分解が必要になります。

繰り返し二乗法

実際の RSA では n も d も600桁級なので、m を d 回掛けるのは不可能です。そこで、掛け算のたびに mod を取って数を小さく保ち、指数を2進数に分解して「2乗」と「掛け算」を組み合わせます。例えば 6517 mod 3233 は、17 = 16 + 1 なので 65 を4回2乗して 6516 を作り、65 を1回掛けるだけで済みます。指数の桁数に比例する回数で計算できるため、巨大な指数でも一瞬です。公開指数に 65537（216＋1）が好まれるのも、この計算が少なくて済むからです。

RSA 計算機小さな素数で全ステップを確認できます

実際の使い方と注意点

上の式をそのまま使う「教科書的 RSA」には弱点があります。同じ平文は常に同じ暗号文になるため、候補が少ない平文は総当たりで当てられます。また、暗号文に細工すると復号結果も予測どおりに変化してしまいます。実用では、暗号化前に OAEP というパディングでランダムな値を混ぜ込みます。署名では同様に PSS を使います。

RSA は共通鍵暗号より桁違いに遅く、一度に暗号化できるのも鍵の大きさより小さなデータだけです。そのため、データ本体は AES で暗号化し、その共通鍵だけを公開鍵暗号で守るハイブリッド暗号が基本形になります。現在の推奨鍵長は2048ビット以上で、長期の利用には3072ビット以上が勧められています。

第6章鍵共有と楕円曲線

Diffie-Hellman（DH）鍵共有は、盗聴されている通信路で、送ったものを全部見られても、2人だけが同じ秘密の値を手に入れる方法です。何かを暗号化して送るのではなく、双方が自分の手元で同じ値を「計算して作る」のが特徴です。

小さな数で試す

公開パラメータを p = 23、g = 5 とします。

クライアントサーバー
秘密の数を選ぶa = 6b = 15
公開値を作って送るA = 5⁶ mod 23 = 8B = 5¹⁵ mod 23 = 19
受け取った値で計算19⁶ mod 23 = 28¹⁵ mod 23 = 2

どちらも gab を計算しているので同じ値になります。盗聴者が見られるのは 23、5、8、19 だけで、「5 を何乗すると23で割った余りが8になるか」を逆算する離散対数問題は、数が大きくなると解けません。

楕円曲線への置き換え

楕円曲線暗号（ECC）では、y² = x³ + ax + b という曲線上の点を使います。曲線上の2点を通る直線と曲線の3つ目の交点を x 軸で折り返す操作を「点の足し算」と定義し、点 G を k 回足したものを kG と書きます。DH の ga が点の掛け算 aG に置き換わり、双方が a(bG) = b(aG) = abG という同じ点を得ます。G と aG から a を求める楕円曲線離散対数問題には、素因数分解のような効率的な近道が知られていないため、ずっと短い鍵で同じ強さが得られます。

128ビット相当AES-1283072ビット256ビット

TLS でよく使われる曲線は X25519 と P-256 です。

使い捨て鍵と前方秘匿性

ECDHE の最後の E は Ephemeral（使い捨て）の意味で、秘密の数を接続ごとに新しく作り、終わったら捨てます。これにより、将来サーバーの長期的な秘密鍵が漏れても、過去に記録された通信は復号できません。この性質を前方秘匿性と呼びます。

DH だけでは中間者攻撃を防げない。 攻撃者が通信の間に入り、双方と別々に鍵共有すれば、どちらにも気づかれずに中身を読めます。そのため、鍵共有の値が本物の相手から来たことをデジタル署名で確認する必要があります。

第7章デジタル署名と証明書

デジタル署名は、公開鍵暗号を逆向きに使う技術です。秘密鍵で署名を作り、公開鍵で誰でも検証できます。作れるのは本人だけ、確かめるのは誰でもできる、という点で、紙の世界の実印と印鑑証明に似ています。

  1. 署名者はメッセージのハッシュ値 h を計算する。
  2. 秘密鍵で署名を作る。RSA なら s = hd mod n。
  3. メッセージと署名 s を送る。
  4. 検証者は公開鍵で se mod n を計算し、自分で計算したメッセージのハッシュ値と一致するか確かめる。

一致すれば、秘密鍵の持ち主が署名したこと（認証）と、メッセージが改ざんされていないこと（完全性）が同時に確認できます。秘密鍵を持つのは本人だけなので否認防止にもなります。メッセージそのものではなくハッシュ値に署名するのは、長いデータでも1回の計算で済むからです。RSA の他、楕円曲線を使う ECDSA や Ed25519 も広く使われています。

公開鍵基盤（PKI）と証明書

署名の検証には相手の公開鍵が必要ですが、その公開鍵が本物かどうかはどう確かめるのでしょうか。偽サーバーが自分の公開鍵を「本物」と言って渡してくる可能性があります。これを解決するのが証明書です。

証明書には「このドメインの公開鍵はこれである」という情報が書かれ、認証局（CA）のデジタル署名が付いています。ブラウザや OS には信頼できるルート認証局の公開鍵があらかじめ組み込まれていて、ルート認証局が中間認証局に署名し、中間認証局がサーバー証明書に署名する、という連鎖をたどって検証します。この連鎖を証明書チェーンと呼びます。証明書には有効期限があり、秘密鍵が漏れた場合などには失効させる仕組みもあります。

第8章TLS 1.3

TLS は HTTPS などで使われる通信の暗号化プロトコルで、これまでの章の技術をすべて組み合わせています。鍵共有に ECDHE、相手の確認に署名と証明書、データの暗号化に AEAD、鍵の導出にハッシュ関数を使います。

  1. クライアントが、対応する暗号方式の一覧と ECDHE の公開値を送る。
  2. サーバーが方式を選び、自分の ECDHE の公開値を返す。この時点で双方が共有秘密を計算でき、以降のメッセージは暗号化される。
  3. サーバーが証明書と、ここまでのやり取りへの署名を送る。クライアントは証明書チェーンをたどって公開鍵を確かめ、署名を検証する。これで中間者攻撃を防ぐ。
  4. 双方が Finished（ハンドシェイク全体の検証値）を送り、改ざんがなかったことを確認する。
  5. 以降は共通鍵による AEAD で高速にデータをやり取りする。

TLS 1.2 まではハンドシェイクに2往復必要でしたが、TLS 1.3 では1往復で済みます。また、前方秘匿性のない RSA 鍵交換や、CBC モード、SHA-1 などの古い方式は TLS 1.3 では使えなくなりました。

第9章身近な暗号

暗号技術はウェブ通信以外にも、日常のさまざまな場面で使われています。

エンドツーエンド暗号化

メッセージアプリの多くは、送信者と受信者の端末だけが鍵を持ち、運営会社のサーバーでも内容を読めないエンドツーエンド暗号化（E2EE）を採用しています。代表的な Signal プロトコルでは、鍵共有に楕円曲線 DH を使い、さらに「ダブルラチェット」という仕組みでメッセージごとに鍵を更新します。ある時点の鍵が漏れても、それ以前とそれ以降のメッセージは守られます。TLS がサーバーまでの通信路を守るのに対し、E2EE は通信相手まで全区間を守る点が違います。

ストレージの暗号化

BitLocker（Windows）や FileVault（macOS）、スマートフォンの端末暗号化は、ディスク全体を AES で暗号化します。暗号化に使う鍵は、端末内の専用チップ（TPM やセキュアエンクレーブ）とパスワードや生体認証で守られており、端末を盗まれても中身を取り出せません。

Wi-Fi

無線 LAN の WPA2 や WPA3 は、端末とアクセスポイントの間の通信を AES で暗号化します。WPA3 ではパスワードから鍵を作る手順に SAE という鍵共有方式を使い、通信を録音してもパスワードを総当たりで推測しにくくなっています。

パスキー

パスワードに代わるログイン方式のパスキー（FIDO2/WebAuthn）は、デジタル署名そのものです。端末がサービスごとに鍵ペアを作り、サービス側には公開鍵だけを登録します。ログイン時はサービスから送られた乱数に秘密鍵で署名して返すため、サーバーから情報が漏れても使えるものがなく、偽サイトでは署名が成立しないのでフィッシングにも強い仕組みです。

第10章量子コンピュータと暗号

十分な規模の量子コンピュータが実現すると、ショアのアルゴリズムによって素因数分解と離散対数問題が効率よく解けるようになります。つまり RSA、DH、楕円曲線暗号といった現在の公開鍵暗号はすべて破られます。一方、共通鍵暗号とハッシュ関数への影響はグローバーのアルゴリズムによる総当たりの高速化にとどまり、鍵長を2倍にすれば対策できると考えられています。このため AES-256 や SHA-384 以上への移行が勧められています。

現時点で暗号を破れる量子コンピュータは存在しませんが、「今のうちに暗号化された通信を保存しておき、将来量子コンピュータで解読する」攻撃（Harvest now, decrypt later）が懸念されています。長期間秘密にすべき情報ほど、早めの対策が必要です。

耐量子暗号

量子コンピュータでも解けないと考えられている数学的問題に基づく暗号を耐量子暗号（PQC）と呼びます。NIST は2024年8月に最初の標準を発行しました。

規格名称用途基盤となる問題
FIPS 203ML-KEM鍵共有（鍵カプセル化）格子問題
FIPS 204ML-DSAデジタル署名格子問題
FIPS 205SLH-DSAデジタル署名ハッシュ関数

移行期には、新しい方式に未知の弱点が見つかる可能性に備えて、従来の暗号と耐量子暗号を組み合わせるハイブリッド方式が使われています。TLS では X25519 と ML-KEM-768 を組み合わせた鍵共有が、主要なブラウザやクラウドサービスで既に有効になっています。どちらか一方が破られても、もう一方が安全なら通信は守られます。

第11章実務での注意点

暗号の失敗の多くは、アルゴリズムが破られることではなく、使い方の誤りから起きます。

用途推奨避けるべき
共通鍵暗号AES-GCM、ChaCha20-Poly1305DES、3DES、RC4、ECB モード
ハッシュSHA-256、SHA-384、SHA-3MD5、SHA-1
パスワード保存Argon2id、scrypt、bcrypt平文、ソルトなし・高速なハッシュ
鍵共有X25519、ECDHE、ハイブリッド PQC前方秘匿性のない RSA 鍵交換
署名Ed25519、ECDSA P-256、RSA-PSS 30721024ビット以下の RSA
通信プロトコルTLS 1.3（互換性が必要なら 1.2）SSL、TLS 1.0、TLS 1.1
  • 暗号を自作しない。 独自のアルゴリズムや、標準部品の独自の組み合わせは、専門家の検証を受けていない限りほぼ確実に弱点を含みます。libsodium や各言語の標準ライブラリなど、実績のある高水準ライブラリを使いましょう。
  • 乱数は暗号論的に安全なものを使う。 鍵やナンスの生成に、Math.random のような予測可能な乱数を使ってはいけません。OS が提供する暗号論的擬似乱数生成器（CSPRNG）を使います。
  • 鍵の管理が本体。 暗号がどれほど強くても、鍵がソースコードに直書きされていたり、ログに出力されていたりすれば意味がありません。鍵は専用の鍵管理サービスやハードウェア（HSM）で保管し、定期的に更新します。
  • 比較は一定時間で行う。 MAC やトークンの比較で、一致しない文字が見つかった時点で処理を終えると、処理時間の差から正解が推測されることがあります（タイミング攻撃）。
  • 暗号の切り替えに備える。 将来のアルゴリズム移行（耐量子暗号など）を見越して、使う方式を設定で差し替えられる設計にしておくことを暗号アジリティと呼びます。
